DATA CODE 2.0 Comité Técnico de Evaluación

Selección de Formato Operativo

Análisis comparativo de viabilidad técnica y desarrollo de software para el despliegue del evento institucional.

Alternativa A

Formato Hackathon

Enfoque tradicional de prototipado rápido

  • Ventana de Ejecución Temporal

    Sprint intensivo de 24 a 48 horas bajo privación de sueño. Obliga a omitir patrones de diseño limpios, generando una alta deuda técnica y código monolítico frágil.

  • Persistencia y Arquitectura de Datos

    Dependencia de prototipos visuales (Mockups) con arreglos estáticos en memoria (Hardcoded). Las consultas SQL no están normalizadas, lo que provoca fallos de integridad referencial ante datos concurrentes.

  • Criterio de Validación Institucional

    Evaluación predominantemente subjetiva basada en la oratoria de ventas (Pitch comercial) y diseño de interfaces de usuario superficiales, tolerando caídas del servidor y ausencia de manejo de excepciones.

RECOMENDADO
Alternativa B

Formato Buildathon

Ingeniería de software y arquitectura escalable

  • Ciclo de Vida del Software (SDLC)

    Desarrollo iterativo estructurado de 3 a 4 semanas. Facilita la aplicación rigurosa de control de versiones (Git), pruebas unitarias en entornos virtuales y refactorización continua de módulos.

  • Infractructura Backend y Base de Datos

    Implementación real en Python (Flask) con enrutamiento WSGI seguro y persistencia en bases de datos relacionales SQLite bajo la Tercera Forma Normal (3NF) para control estricto de aforos y matrículas.

  • Aseguramiento de Calidad (QA & DevOps)

    Auditoría técnica exhaustiva que verifica la sanitización de entradas, prevención de inyecciones SQL, manejo robusto de excepciones (Edge Cases) y viabilidad de despliegue en servidores de producción.
